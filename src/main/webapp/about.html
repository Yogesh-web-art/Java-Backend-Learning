About Spring JDBC

A practical guide to database access with Spring: write SQL clearly, let Spring manage JDBC boilerplate, and keep data operations testable and reliable.

1. What is Spring JDBC?

Spring JDBC is the Spring Framework's SQL database-access support. It keeps ordinary JDBC and SQL available while handling repetitive infrastructure work such as obtaining and releasing connections, creating and closing statements and result sets, and translating SQL exceptions into Spring's consistent data-access exception hierarchy.

You still design the schema, write SQL, choose transaction boundaries, and map query results. Spring reduces low-level plumbing; it does not hide SQL or turn a relational database into an object-relational mapping system.

In one sentence: Spring JDBC combines explicit SQL with Spring-managed connections, parameter binding, result mapping, transactions, and consistent exception handling.

Spring JDBC and related technologies

Spring JDBC is distinct from Spring Data JPA, Hibernate, and other ORM solutions: it does not automatically persist an object graph or generate all SQL from entity mappings. It is a good fit when SQL clarity, direct control over database operations, or a relatively small persistence abstraction is desired. Spring Boot can auto-configure a DataSource and JDBC support, but Boot and Spring JDBC are different parts of the ecosystem.

2. JDBC foundations

Java Database Connectivity (JDBC) is the Java API for communicating with relational databases. A typical operation obtains a Connection, prepares a PreparedStatement, binds values, executes SQL, reads a ResultSet, and releases resources. A JDBC driver implements the database-specific wire protocol.

JDBC is flexible, but application code must carefully handle resource cleanup, exception conversion, connection management, and repetitive result-set traversal. Spring JDBC builds on this API and applies consistent resource-management patterns.

Where the pieces fit

  • Application/DAO layer: defines operations and SQL appropriate to the application.
  • Spring JDBC helper: executes statements, binds parameters, processes results, and converts errors.
  • DataSource: supplies database connections, usually through a connection pool.
  • JDBC driver and database: execute SQL and return results.

3. DataSource and connection management

A DataSource is the standard JDBC abstraction used to obtain connections. Configure it with the JDBC URL, driver, credentials, and pool settings. In production, an application generally uses a connection pool so opening a logical connection borrows a reusable physical database connection rather than establishing a new network connection for each operation.

Spring JDBC helpers obtain connections from the DataSource and release them when the operation is complete. When a Spring transaction is active, Spring coordinates the connection with that transaction instead of prematurely closing it. Do not manually close a connection managed by Spring callbacks or retrieve connections outside the configured transaction context.

Connection pool considerations

  • Choose a pool supported by the application platform and set pool size and timeouts for the workload.
  • Use least-privilege database credentials and keep secrets out of source code.
  • Close or release manually acquired JDBC resources with try-with-resources when not using Spring's templates.
  • Size pools with database capacity and all application instances in mind.

4. JdbcTemplate

JdbcTemplate is the central Spring JDBC helper. Create it with a configured DataSource, usually once and share it as a thread-safe application bean. It executes SQL and handles connection/statement/result-set lifecycle, resource cleanup, and exception translation.

Common methods include query for reading rows, queryForObject for a single value or row, queryForList for simple collections, update for insert/update/delete statements, execute for lower-level work, and batchUpdate for batches.

Templates are stateless helpers, not a place to store per-request data. Pass SQL parameters and row-mapping callbacks into each operation. Use the overload whose expected result matches the query and handle a missing row or unexpected row count deliberately.

JdbcClient

In Spring Framework 6.1 and later, JdbcClient offers a fluent API for executing SQL with named or positional parameters. It delegates to the JDBC template infrastructure. It is an optional newer facade; use APIs supported by the Spring version in your application.

5. Queries, inserts, updates, and deletes

A query can map rows into domain objects or return scalar values. An update operation executes statements that modify data and commonly returns the number of affected rows. Use that count when it matters—for example, to detect an update that did not find the expected record.

  • Read one value: use a single-value query such as queryForObject with an appropriate result type.
  • Read objects: use query with a row mapper to convert each row.
  • Insert/update/delete: use update with bound parameters and inspect the returned row count when useful.
  • Custom JDBC work: use callbacks such as PreparedStatementCreator or ConnectionCallback only when a simpler template method is insufficient.

SQL syntax, pagination, generated-key behavior, and some types vary by database. Keep database-specific statements and migrations deliberate rather than assuming all SQL dialects behave identically.

6. Mapping result sets to objects

A RowMapper converts the current row of a ResultSet into one object. It is a common way to map query results into a domain type or data-transfer object. Spring invokes it for each row and collects the mapped results.

BeanPropertyRowMapper can map columns to bean properties by name conventions. It is convenient for simple cases, but explicit row mappers provide more control over null handling, type conversion, naming differences, and complex mappings. A ResultSetExtractor processes an entire result set and is useful when rows need to be grouped into a more complex structure.

Be explicit about nullable columns, timestamps, numeric conversions, and joins that repeat parent columns. Avoid selecting unused columns; keep SQL projections aligned with the data the operation needs.

7. Parameters, named parameters, and SQL safety

Use prepared-statement placeholders for values and bind the values separately from SQL text. Parameter binding prevents user-supplied values from being interpreted as SQL syntax and helps avoid SQL injection.

NamedParameterJdbcTemplate lets SQL use readable names such as :customerId and accepts a parameter map or source. It can expand collection parameters for an IN clause. Positional parameters in JdbcTemplate use ? placeholders and must be supplied in the correct order.

Placeholders represent values, not table names, column names, or sort directions. If a query must vary identifiers or ordering, select those fragments from a strict allow-list; never concatenate unchecked user input into SQL.

8. Batches, generated keys, and database routines

  • Batch updates: batchUpdate groups repeated statements, reducing round trips for bulk writes. Batch size, driver behavior, error reporting, and transaction boundaries still matter.
  • Generated keys: JDBC key holders and generated-key options can capture database-generated identifiers after an insert. Support depends on the driver and database.
  • SimpleJdbcInsert: wraps insert operations and can return generated keys when configured with a DataSource and table metadata or explicit column information.
  • Stored procedures: SimpleJdbcCall helps call stored procedures or functions; declare parameters when metadata discovery is unsuitable or unreliable.
  • Low-level callbacks: template callbacks allow controlled access to JDBC APIs for special cases while Spring still manages the surrounding resources.

9. Transaction management

Transactions group database operations so they commit together or roll back together. Spring provides a consistent transaction abstraction. For JDBC, a PlatformTransactionManager such as DataSourceTransactionManager coordinates a DataSource connection. In many applications, @Transactional declares a service-level transaction; programmatic code can use TransactionTemplate.

Transaction behavior depends on configuration and proxy boundaries. In proxy-based declarative transactions, calls must pass through the Spring proxy; self-invocation may not activate transaction advice. By default, Spring commonly rolls back on unchecked exceptions, while checked-exception behavior can be configured. Choose propagation and isolation intentionally and keep transactions no longer than needed.

Transactions do not make every external effect atomic: a database rollback cannot undo an email or an unrelated HTTP request. Coordinate external side effects with a suitable application design.

10. Exception translation

Raw JDBC reports SQLException values with vendor-specific codes and messages. Spring translates JDBC errors into the unchecked DataAccessException hierarchy, giving application code a more consistent abstraction across database vendors.

Translated exceptions can describe categories such as duplicate keys, integrity violations, invalid data access, or resource failures. Catch exceptions when the application can meaningfully recover, add context, or return a deliberate result. Avoid swallowing database failures or converting every exception into a success-shaped response.

11. Configuration and application structure

Define a DataSource and JDBC helper as Spring-managed beans, or let Spring Boot auto-configure them from application settings and classpath dependencies. Keep credentials and environment-specific URLs external to source control. A persistence component—often a repository or DAO—uses the JDBC helper; a service defines the application operation and its transaction boundary.

JdbcDaoSupport is a legacy support base class that exposes a JdbcTemplate from a DataSource. Modern designs commonly prefer constructor injection of JdbcTemplate or NamedParameterJdbcTemplate into a focused repository instead of inheriting support classes.

Schema changes should be versioned and reproducible, typically with a database migration tool. Keep schema initialization for development/test separate from production migration policy.

12. Testing Spring JDBC code

Test repository SQL against a real or embedded database that behaves sufficiently like the production database. Spring's test support, including @JdbcTest where available, can configure a focused JDBC test slice. Test slices and embedded-database replacement behavior depend on Spring Boot and test dependencies.

  • Cover successful reads and writes, empty results, null values, and row-count behavior.
  • Test transaction rollback and constraints when those behaviors are important.
  • Use the production database engine in integration tests when SQL dialect, driver, or vendor behavior matters.
  • Keep unit tests for service logic separate from tests that need a database and Spring context.

13. Best practices and common pitfalls

  • Use parameter binding; never concatenate untrusted values into SQL.
  • Keep SQL readable and test it against the database dialect actually deployed.
  • Use a managed connection pool and set timeouts and capacity deliberately.
  • Keep transaction boundaries at meaningful service operations and avoid long-running transactions.
  • Use focused row mappers and explicit column lists; handle nulls and missing rows deliberately.
  • Use batch operations for repeated writes when appropriate, while checking partial failures and transaction behavior.
  • Do not swallow DataAccessException or leak credentials into logs.
  • Remember Spring JDBC manages JDBC boilerplate but does not replace relational modeling, SQL design, indexing, or database migrations.

14. Quick glossary

  • JDBC: Java's API for communicating with relational databases.
  • DataSource: the standard factory for database connections, commonly backed by a pool.
  • JdbcTemplate: Spring's helper for executing SQL and managing JDBC resources.
  • RowMapper: converts one result-set row into an object.
  • NamedParameterJdbcTemplate: JDBC helper that binds readable named SQL parameters.
  • DataAccessException: Spring's translated unchecked data-access exception family.
  • Transaction manager: coordinates commit and rollback around a unit of work.
  • Batch update: executes many similar statements with fewer database round trips.
