1. What is Spring Core?

Spring is an open-source Java framework for building applications. Spring Core is the foundation of the Spring Framework: it supplies the IoC container, dependency injection (DI), bean configuration and lifecycle, and common utilities used by higher-level Spring modules.

Instead of application classes constructing and locating every collaborator themselves, Spring can create objects, connect their dependencies, and manage their lifecycle. This reduces coupling and makes components easier to configure, replace, and test.

In one sentence: Spring Core manages application objects and their relationships from configuration, so application code can focus on behavior rather than wiring.

What Spring Core is—and is not

Spring Core is not a programming language, a replacement for the JVM, or a complete application by itself. It is the framework foundation. Spring MVC, Spring Data, Spring Security, Spring Boot, and other projects build on or integrate with the Spring Framework; they are related, but are not all Spring Core features.

2. Inversion of Control and Dependency Injection

Inversion of Control (IoC)

Without a container, a class often creates its own dependencies with new. With IoC, control of object creation and assembly is moved from application code to a framework or container. The application describes components and their relationships; the container supplies them.

Dependency Injection (DI)

DI is a common way to implement IoC. A class declares what it needs, and Spring provides those dependencies. For example, an order service can receive a repository rather than constructing a concrete database repository itself.

  • Constructor injection: dependencies are constructor parameters. It makes required dependencies explicit, supports immutable fields, and is generally the preferred choice.
  • Setter injection: dependencies are supplied through setters; useful for optional or reconfigurable dependencies.
  • Field injection: dependencies are written directly into fields, commonly using annotations. It is concise but hides requirements and makes plain unit testing harder; constructor injection is usually preferable.

DI improves separation of concerns and supports substituting implementations (for example, a real repository in production and a fake in a unit test). It does not remove the need to design clear interfaces and responsibilities.

3. The IoC container

The container reads configuration metadata, creates and configures beans, resolves dependencies, and manages lifecycle callbacks. Its central interfaces are:

  • BeanFactory: the basic container contract for obtaining beans and wiring dependencies. Implementations can create beans lazily.
  • ApplicationContext: a richer, commonly used container built on the BeanFactory model. It adds features such as application events, internationalized messages, resource loading, and integration with framework facilities.

Common contexts include AnnotationConfigApplicationContext for Java/annotation configuration and web-specific contexts in web applications. Spring Boot typically creates and configures the application context for you.

High-level startup sequence

  1. Load configuration and register bean definitions.
  2. Run factory-level customization and register post-processors.
  3. Instantiate beans as needed (many singleton beans are created during context startup), resolve dependencies, and apply bean post-processors.
  4. Use the configured objects; close the context when its owner is finished so destruction callbacks can run.

4. Beans and bean definitions

A Spring bean is an object instantiated, assembled, or otherwise managed by a Spring container. A bean definition is the metadata describing how to create and configure that object: its class, constructor arguments, properties, scope, lifecycle methods, qualifiers, and other settings.

Beans may be application services, repositories, controllers, configuration objects, third-party library objects, or infrastructure collaborators. Not every Java object must be a bean.

Finding and identifying beans

  • @Component marks a general component for scanning.
  • @Service, @Repository, and @Controller are specialized component stereotypes that communicate intent (and can enable related framework behavior).
  • @Bean on a method in a configuration class explicitly registers the method's returned object as a bean. This is particularly useful for configuring third-party types.
  • XML and programmatic registration can also define beans.

Choosing among beans

When several beans satisfy one dependency, use @Primary to designate a default or @Qualifier to select a named/qualified candidate. Prefer meaningful qualifiers over relying on accidental class names. Circular dependencies usually indicate tightly coupled design; refactor the responsibilities rather than treating a cycle as a normal wiring pattern.

5. Configuration styles and annotations

Java configuration

@Configuration declares a source of bean definitions; methods annotated with @Bean provide instances. Component scanning with @ComponentScan discovers stereotype-annotated classes. Java configuration is type-aware and works well with modern Spring applications.

Annotation-based component configuration

Annotations such as @Autowired request dependency resolution; @Value injects a value or expression; @Qualifier disambiguates a candidate; and @Lazy can defer instantiation. Spring can often infer a single constructor, so @Autowired is not always necessary on that constructor.

XML configuration

XML declares beans and properties outside Java classes. It remains useful in legacy systems and some integration scenarios. XML and annotation/Java configuration can coexist, though a project should keep configuration understandable and avoid duplicate definitions.

Externalized values and profiles

Use properties or environment-backed configuration for deployment-specific values instead of hard-coding them in components. Profiles (for example, @Profile) enable environment-specific bean definitions. Keep secrets out of source control and inject them through a secure configuration mechanism.

Autowiring and resolution

Spring resolves a dependency primarily by type, then uses qualifiers, primary status, names, and other available metadata where applicable. Explicit constructors and narrow interfaces make wiring easier to reason about than broad, implicit dependencies.

6. Bean lifecycle, scopes, and extension points

Lifecycle

Spring can call initialization callbacks after dependency injection and destruction callbacks when a managed context shuts down. Common approaches include @PostConstruct and @PreDestroy (Jakarta annotations in modern Spring generations), InitializingBean/DisposableBean, or custom init/destroy method names. Annotation package availability depends on the Spring/Jakarta version in use. Keep callbacks short; expensive work and external resources need deliberate startup/shutdown handling.

Bean scopes

  • Singleton: one shared bean instance per bean definition per container; it is Spring's common default. It does not mean one instance for the entire JVM.
  • Prototype: a new instance is created when requested from the container. Spring does not manage the complete destruction lifecycle of prototype instances.
  • Request and session: web-aware scopes create instances associated with an HTTP request or session.
  • Application and WebSocket: additional scopes are available in applicable web environments.

Injecting a shorter-lived scoped object into a longer-lived singleton may require a scoped proxy or provider so the right instance is resolved at the right time.

Container extension points

BeanFactoryPostProcessor can customize bean-definition metadata before ordinary beans are created. BeanPostProcessor can inspect or wrap bean instances around initialization; framework features such as proxy creation use this kind of extension. These are powerful infrastructure hooks and should be used carefully.

“Aware” interfaces (such as BeanNameAware or ApplicationContextAware) let a bean request container infrastructure details. Prefer ordinary DI for application dependencies; using Aware callbacks can couple a component to Spring.

7. Other Spring Core container services

  • Resource abstraction: Resource and ResourceLoader provide a consistent way to access classpath, filesystem, URL, and other resources.
  • Application events: publish and handle application-level events with the event publisher and listeners such as @EventListener. Events can decouple components, but are not a substitute for durable messaging.
  • Internationalization: MessageSource resolves locale-specific messages from configured bundles.
  • Type conversion and formatting: convert values between types and format values for display or binding through conversion/formatter infrastructure.
  • Validation: Spring integrates validation abstractions and commonly integrates with Jakarta Bean Validation providers; exact APIs depend on the Spring generation.
  • SpEL: the Spring Expression Language can evaluate expressions in supported configuration and framework contexts. Expressions should be controlled and not built from untrusted input.
  • Data binding: bind and convert property values to object properties in supported contexts.
  • Task execution: abstractions such as task executors and schedulers help integrate asynchronous or scheduled work when configured.

8. Spring AOP

Aspect-oriented programming modularizes cross-cutting concerns—behavior that applies across multiple components, such as transaction boundaries, security checks, or logging. Spring AOP commonly uses runtime proxies around Spring-managed objects.

  • Aspect: a module containing cross-cutting behavior.
  • Join point: a point during execution where behavior can be applied; Spring proxy-based AOP primarily intercepts method execution.
  • Pointcut: a predicate selecting join points.
  • Advice: code run before, after, or around selected execution.
  • Target and proxy: the target is the underlying object; callers interact through a proxy that can apply advice.

Proxy-based AOP has limits: self-invocation may bypass the proxy, and only calls that pass through the proxy are advised. It is distinct from AspectJ's broader weaving approach. Use AOP for genuinely cross-cutting behavior, not to obscure ordinary business flow.

9. Core packages, related modules, and integration

The Spring Framework is organized into modules. The core container includes foundational packages often described as Core, Beans, Context, and Expression (SpEL). Other framework modules provide AOP, data access/transactions, web/servlet, messaging, and testing features. Availability and package details vary by Spring Framework version.

Spring Core is the base for higher-level modules and integrates with Java libraries and application servers. Spring Boot is a separate project that simplifies Spring application setup and deployment; it uses the Spring Framework but is not synonymous with Spring Core. Spring Data, Spring Security, and Spring MVC are also distinct projects/modules.

Typical application wiring

A configuration class or component scan registers an interface implementation as a bean; a service receives that interface through its constructor; the container resolves the matching bean; and the application context coordinates the component lifecycle. Higher-level features can add proxies or listeners around those components.

10. Testing Spring applications

Constructor-injected classes can often be tested as plain Java objects by passing fakes or mocks directly, without starting Spring. Use a Spring test context when the behavior under test depends on actual configuration, bean resolution, proxies, or framework integration.

  • Test business behavior separately from container wiring where possible.
  • Use focused context tests to verify configuration and bean selection.
  • Use the Spring TestContext Framework and compatible test integrations for context lifecycle and test support.
  • Do not start a full application context for every small unit test unless the test requires it.

11. Best practices and common pitfalls

  • Prefer constructor injection for required dependencies, and keep constructors and components focused.
  • Depend on interfaces or stable abstractions where that helps independent testing and implementation choice.
  • Keep business logic out of configuration classes and lifecycle callbacks.
  • Use scopes intentionally; remember singleton beans are shared and should not keep unsafe mutable per-request state.
  • Resolve multiple candidates explicitly with qualifiers or a deliberate primary bean.
  • Keep configuration consistent, externalize environment-specific values, and protect secrets.
  • Avoid circular dependencies, excessive container lookups, and unnecessary Aware coupling.
  • Understand proxy boundaries when using AOP or proxy-based framework features.
  • Choose Spring/Jakarta APIs that match the versions in your project; package names and supported Java versions evolve.

12. Quick glossary

  • IoC: transferring control of object creation/wiring to a container.
  • DI: providing an object's dependencies from outside that object.
  • Bean: an object managed by a Spring container.
  • Bean definition: metadata describing a bean and how it is configured.
  • BeanFactory: the basic Spring container abstraction.
  • ApplicationContext: a richer container adding common application services.
  • Scope: the lifecycle/visibility rules for bean instances.
  • Pointcut/advice: where AOP applies and what it runs there.
  • Proxy: a stand-in object that can add behavior around calls to a target.
